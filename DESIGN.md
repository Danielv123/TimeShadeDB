# timeShadeDB design plan

## Goal

Build a Go database for continuously ingesting Factorio charted-chunk snapshots
and querying map pixels over time.

The live input is generated by a Factorio mod as TSV rows shaped like:

```text
game_tick	surface	chunk_x	chunk_y	force	colordata
```

`colordata` is RGB565 data for one `32x32` chunk:

```text
32 * 32 * 2 = 2048 bytes
```

The server receives those rows over HTTP while it is also serving query traffic.
The primary ingest endpoint is:

```text
POST /api/ingest/chunk/{savefile_uuid}
Content-Type: text/tab-separated-values
```

The request body may contain one TSV row or multiple newline-delimited TSV rows.
For every row, the server derives a datastore key:

```text
datastore_key = savefile_uuid + surface + force
```

Each datastore has its own live in-memory map, chunk indexes, append-only data
files, and stats. A single server process can therefore ingest and serve many
save files, surfaces, and forces without a separate database process per world.

The core model is:

1. Keep the latest chunk pixels in memory per datastore.
2. Decode each incoming RGB565 chunk snapshot.
3. Compare it against that datastore's live in-memory chunk.
4. Discard pixels that did not change.
5. Append only changed pixels to per-chunk delta logs.
6. Periodically save compressed full chunk snapshots.
7. Answer historical queries by loading the latest snapshot at or before the
   requested tick, then replaying deltas forward.

## Input Format

### HTTP endpoint

```text
POST /api/ingest/chunk/{savefile_uuid}
```

Path parameters:

```text
savefile_uuid  stable UUID for the Factorio save file
```

Body format:

```text
game_tick	surface	chunk_x	chunk_y	force	colordata
```

Field meanings:

```text
game_tick   Factorio game tick, stored as uint64
surface     Factorio surface name
chunk_x     signed chunk coordinate
chunk_y     signed chunk coordinate
force       Factorio force name
colordata   encoded RGB565 pixels for a 32x32 chunk
```

The `colordata` wire encoding must be explicit in the implementation. Preferred
wire encoding is base64 over the raw 2048 RGB565 bytes because it is safe in TSV
and HTTP text bodies:

```text
base64(raw little-endian RGB565 bytes)
```

If the mod currently emits hex or escaped binary instead, add that decoder
behind the same parser, but keep the internal representation as `[]uint16`
RGB565 values.

Validation rules:

- reject rows with the wrong number of fields;
- reject malformed save UUIDs;
- reject empty `surface` or `force`;
- reject non-integer ticks or chunk coordinates;
- reject decoded color payloads that are not exactly `2048` bytes;
- reject unsupported color payload encoding with a clear `400` response;
- count accepted rows, changed pixels, unchanged pixels, and rejected rows.

### Response

The endpoint returns JSON:

```json
{
  "accepted_rows": 10,
  "changed_pixels": 1523,
  "unchanged_pixels": 8717,
  "datastores_touched": 2
}
```

Partial success should be avoided for normal clients. If any row is invalid, the
first implementation can reject the whole request. If later we need high-volume
best-effort ingestion, add a batch result format with per-line errors.

### Ingest metadata endpoint

The database should expose metadata about the latest accepted data so external
senders can resume after being offline:

```text
GET /api/ingest/chunk/{savefile_uuid}/meta
```

The response should include the newest accepted tick per `(surface, force)` and,
where needed for deterministic resume, the last accepted row identity:

```json
{
  "savefile_uuid": "00000000-0000-0000-0000-000000000000",
  "datastores": [
    {
      "surface": "nauvis",
      "force": "player",
      "latest_tick": 123456,
      "latest_chunk_x": 10,
      "latest_chunk_y": -4,
      "latest_row_seq": 98765
    }
  ]
}
```

`latest_tick` alone is not always enough because several chunks can be charted
on the same tick. The sender should resume from the last matching row and then
continue with subsequent rows, or resend rows from that tick and let the server
deduplicate unchanged pixels.

## Assumptions

- One Factorio chunk is always `32x32` pixels.
- Pixels are stored internally as RGB565 `uint16`, not palette IDs.
- Tick timestamps are stored as `uint64` Factorio game ticks.
- Chunk coordinates are signed integers and can be negative.
- Map bounds are dynamic. New chunks are created on first ingest.
- A datastore is identified by `(savefile_uuid, surface, force)`.
- Latest-state data is always available in memory while the server is running.
- Historical durability comes from append-only chunk data files and chunk
  indexes. There is no separate tile directory or write-ahead-log directory in
  the chunk format.

## Public API

The library should expose chunk-oriented APIs. The old r/place placement API can
remain temporarily for migration tests, but the new storage path should be
driven by chunk snapshots.

```go
type DB struct {
    // internal fields
}

type OpenOptions struct {
    Path      string
    ReadOnly  bool
    CacheSize int64
}

type DatastoreKey struct {
    SavefileUUID string
    Surface      string
    Force        string
}

type ChunkCoord struct {
    X int32
    Y int32
}

type ChunkIngest struct {
    Key    DatastoreKey
    Tick   uint64
    Chunk  ChunkCoord
    Pixels []uint16 // 1024 RGB565 values, row-major
}

type ChunkAtOptions struct {
    Key   DatastoreKey
    Tick  uint64
    Chunk ChunkCoord
}

type ChunkResult struct {
    Key         DatastoreKey
    Chunk       ChunkCoord
    Tick        uint64
    Width       int
    Height      int
    Pixels      []uint16 // row-major RGB565
    SnapshotTick uint64
    Replayed    int
}

func Open(opts OpenOptions) (*DB, error)
func (db *DB) IngestChunk(ctx context.Context, in ChunkIngest) (*IngestChunkResult, error)
func (db *DB) ChunkAt(ctx context.Context, opts ChunkAtOptions) (*ChunkResult, error)
func (db *DB) Close() error
```

CLI commands should be adjusted around the new format:

```text
timeshadedb serve --db db.tshd
timeshadedb import-chunk-tsv --input chunk-charted.tsv --savefile UUID --db db.tshd
timeshadedb tail-chunk-tsv --input chunk-charted.tsv --savefile UUID --base-url http://127.0.0.1:8080
timeshadedb query-chunk --db db.tshd --savefile UUID --surface nauvis --force player --tick 123456 --chunk 10,-4 --out chunk.rgb565
timeshadedb stats --db db.tshd
timeshadedb inspect-index --db db.tshd --savefile UUID --surface nauvis --force player --chunk 10,-4
```

## In-memory layout

The server keeps a registry of active datastores:

```go
type datastoreState struct {
    Key    DatastoreKey
    Chunks map[ChunkCoord]*chunkState
}
```

Each chunk stores the latest known pixels:

```go
type chunkState struct {
    X int32
    Y int32

    Pixels [1024]uint16
    Seen   bool

    LastSnapshotTick      uint64
    ChangesSinceSnapshot int
    DeltaBytesSinceSnap  int64
    LastSnapshotBytes    int64

    ActiveDeltaBlock DeltaBlockBuilder
}
```

Memory use is proportional to charted chunks:

```text
bytes_per_live_chunk = 32 * 32 * 2 = 2048 bytes
```

Plus map/index overhead. This is acceptable for live serving because Factorio
charting usually touches far fewer chunks than a dense unbounded world.

When a TSV row arrives:

1. Resolve or create the datastore for `(savefile_uuid, surface, force)`.
2. Resolve or create the chunk state for `(chunk_x, chunk_y)`.
3. Decode the incoming `colordata` into 1024 RGB565 values.
4. Compare each incoming pixel with the live chunk snapshot.
5. For changed pixels, update the live snapshot and append delta events.
6. Drop unchanged pixels.
7. Flush frames or snapshots according to the chunk heuristic.

## Ingestion Pipeline

The live HTTP path should be bounded and backpressured:

```text
HTTP request -> TSV parser -> datastore router -> chunk worker -> chunk frame writer
```

### HTTP reader

The request body is streamed line-by-line. The handler should enforce a maximum
body size and a maximum line length so malformed clients cannot force unbounded
memory use.

Useful defaults:

```text
max_rows_per_request = 4096
max_line_bytes = 8192
```

`8192` bytes is enough for a base64-encoded 2048-byte payload plus metadata.

### Parser

Parser output is compact and already decoded:

```go
type ParsedChunk struct {
    Seq    uint64
    Key    DatastoreKey
    Tick   uint64
    Chunk  ChunkCoord
    Pixels [1024]uint16
}
```

Sequence numbers preserve request order. For the same datastore and chunk,
events with the same tick must be applied in input order.

### Datastore router

The router maps `(savefile_uuid, surface, force)` to a datastore. Datastores are
created lazily when the first row for a key arrives.

Names from the request are not used directly as directory names. Store the
original names in metadata and use a stable escaped or hashed path component on
disk.

### Chunk workers

Each active chunk should have a single owner for mutation. The owner:

1. Reads the live `Pixels` array.
2. Builds a delta event for every changed pixel.
3. Updates the live `Pixels` array.
4. Appends changed events directly to the chunk `.cdat` file.
5. Updates the chunk `.cidx` sidecar atomically.
6. Schedules snapshot writes when thresholds are reached.

Chunk-level ownership avoids locks on the hot pixel arrays. A fixed worker pool
can own many chunks by hashing `(datastore_key, chunk_x, chunk_y)` to a queue.

### Query visibility

Latest queries should read from the live in-memory snapshot when the requested
tick is greater than or equal to the newest known tick for that chunk.

Historical queries use on-disk snapshots and deltas. If a query intersects an
active unflushed delta block, it must also replay the in-memory active events or
force a flush before answering.

## On-disk layout

Use one top-level database directory containing many datastores:

```text
db.tshd/
  manifest.json
  datastores/
    {datastore_id}/
      metadata.json
      chunks/
        cx_-000001_cy_000010.cdat
        cx_-000001_cy_000010.cidx
        cx_000000_cy_000010.cdat
        cx_000000_cy_000010.cidx
```

`datastore_id` is a stable hash or escaped identifier derived from:

```text
savefile_uuid + "\x00" + surface + "\x00" + force
```

`metadata.json` stores the original key:

```json
{
  "savefile_uuid": "00000000-0000-0000-0000-000000000000",
  "surface": "nauvis",
  "force": "player",
  "chunk_size": 32,
  "pixel_format": "rgb565",
  "timestamp_unit": "factorio_tick"
}
```

### manifest.json

Human-readable database metadata:

```json
{
  "format": "timeShadeDB",
  "version": 2,
  "chunk_size": 32,
  "pixel_format": "rgb565",
  "timestamp_unit": "factorio_tick",
  "codec": "zstd",
  "codec_level": 9
}
```

### Chunk data file: `chunks/cx_*_cy_*.cdat`

Each chunk data file is a sequence of independently compressed frames. A frame
is either a full chunk snapshot or a delta frame. The sidecar index records each
frame's offset and length.

File header:

```text
magic       4 bytes "CDAT"
version     uint16
chunk_x     int32
chunk_y     int32
chunk_size  uint16 // 32
pixel_format uint16 // 1=RGB565
```

Frame header, stored uncompressed before each zstd payload:

```text
frame_magic      4 bytes "CFRM"
frame_kind       uint8  // 1=snapshot, 2=delta
tick             uint64 // snapshot tick or first delta event tick
max_tick         uint64 // same as tick for snapshots
event_count      uint32 // 0 for snapshots
raw_len          uint32
compressed_len   uint32
checksum         uint32 // payload checksum after decompression
payload          compressed_len bytes, one complete zstd frame
```

Snapshot payload, before compression:

```text
pixels [1024]uint16 // row-major RGB565, little-endian
```

Delta payload, before compression:

```text
magic       4 bytes "CDEL"
version     uint16
event_count uint32
base_tick   uint64
events      repeated event_count
```

Event encoding:

```text
dt_tick uvarint // tick delta from previous event in this frame
pos     uvarint // local row-major pixel index, 0..1023
color   uint16  // RGB565, little-endian
seq     uvarint // optional tie-breaker for same-tick events
```

Events remain in per-chunk ingest order. During replay, apply all events with
`tick <= requested_tick`, preserving sequence order for equal ticks.

### Chunk index sidecar: `chunks/cx_*_cy_*.cidx`

Each chunk has a compact binary index sidecar loaded on demand or at datastore
open.

Header:

```text
magic              4 bytes "CIDX"
version            uint16
chunk_x            int32
chunk_y            int32
chunk_size         uint16
data_file_size     uint64
snapshot_count     uint32
delta_frame_count  uint32
```

Snapshot index record:

```text
tick                   uint64
frame_offset           uint64
frame_header_len       uint16
compressed_len         uint32
raw_len                uint32
first_delta_frame_idx  uint32
event_seq              uint64
checksum               uint32
```

Delta frame index record:

```text
min_tick        uint64
max_tick        uint64
frame_offset    uint64
frame_header_len uint16
compressed_len  uint32
raw_len         uint32
event_count     uint32
first_event_seq uint64
last_event_seq  uint64
checksum        uint32
```

## Snapshot Heuristic

Snapshots are adaptive per chunk. A quiet chunk should not be snapshotted often;
an active chunk should not accumulate long replay chains.

Create a snapshot at a delta frame boundary when any of these are true:

```text
changes_since_snapshot >= 512
delta_compressed_bytes_since_snapshot >= 0.75 * last_snapshot_compressed_bytes
ticks_since_snapshot >= 60 * 60 and changes_since_snapshot > 0
ticks_since_snapshot >= 60 * 60 * 10 even if activity is low
```

At 60 ticks per second, those time thresholds are roughly 1 minute and 10
minutes. They should be configurable because Factorio servers can run at
different speeds.

Rationale:

- `512` changed pixels caps worst-case replay at half a chunk.
- The compressed-size rule avoids long delta chains once a new snapshot is
  similarly cheap.
- The tick rule gives predictable query latency for arbitrary ticks.

Metrics to record per chunk:

```text
snapshot_count
average_snapshot_compressed_bytes
delta_frame_count
average_delta_frame_compressed_bytes
max_replay_events_between_snapshots
unchanged_pixels_discarded
changed_pixels_stored
latest_tick
```

## Delta Frame Sizing

Flush an active delta frame when either condition is met:

```text
event_count >= 4096
tick_span >= 3600
```

For a 32x32 chunk, `4096` events represents four fully changed chunks in one
delta frame. The tick-span rule avoids leaving long-lived unclosed frames for
quiet chunks.

## Query Algorithm

For `ChunkAt(key, tick, chunk)`:

1. Resolve the datastore key.
2. Resolve the chunk index.
3. If the request is for the newest known state, return a copy of the live
   in-memory chunk.
4. Binary-search latest snapshot with `snapshot.tick <= requested_tick`.
5. Seek to the snapshot frame offset in the chunk `.cdat` file.
6. Decompress that single snapshot frame into a caller-owned buffer.
7. Iterate delta frame index records from `snapshot.first_delta_frame_idx`.
8. Stop before the first frame with `min_tick > requested_tick`.
9. Seek to and decompress only needed delta frames.
10. Apply events in order while `event.tick <= requested_tick`.
11. Replay active unflushed events if they overlap the requested tick.
12. Return row-major RGB565 pixels.

For map tile rendering, convert requested world tile bounds into chunk ranges,
load the required chunks, and convert RGB565 to RGBA or indexed PNG output at
the HTTP boundary.

## Durability Model

Continuous ingestion is the primary mode, so the chunk frame files are also the
durability log. Avoid maintaining a second WAL format beside `.cdat` / `.cidx`.

Writer flow:

1. Update the live in-memory chunk snapshot.
2. Append a snapshot or delta frame header and compressed payload to `.cdat`.
3. Flush the chunk data file.
4. Write `*.cidx.tmp`.
5. Atomically rename `*.cidx.tmp` to `*.cidx`.
6. On startup, ignore any trailing `.cdat` frame not referenced by `.cidx`.

On startup:

1. Load manifests and datastore metadata.
2. Load chunk indexes.
3. Rebuild the latest in-memory snapshot for active chunks from the latest
   snapshot plus deltas.
4. Resume ingest.

## Multithreading Plan

Recommended goroutines:

```text
HTTP handler goroutines
1 parser/router per request, bounded by server limits
N chunk worker queues, default runtime.NumCPU()
M compression workers, default max(1, runtime.NumCPU()/2)
1 datastore/index coordinator
```

Chunk work is routed by hash:

```text
hash(datastore_id, chunk_x, chunk_y) % worker_count
```

This gives a single mutation owner for each live chunk while avoiding one
goroutine per chunk.

Backpressure should be explicit:

```go
parsedChunks := make(chan ParsedChunk, maxRowsPerRequest)
workerQueues := make([]chan ParsedChunk, workerCount)
compressionJobs := make(chan CompressionJob, 2*numCPU)
```

If queues are full, the HTTP handler should block up to a timeout and then
return `503` so the local sender can retry.

## TSV Tail Sender

Add a small companion tool that runs on the Factorio host and streams new rows
from the mod's `chunk-charted.tsv` file to the database:

```text
timeshadedb tail-chunk-tsv --input chunk-charted.tsv --savefile UUID --base-url http://127.0.0.1:8080
```

Startup behavior:

1. Call `GET /api/ingest/chunk/{savefile_uuid}/meta`.
2. Read the existing TSV file from the beginning.
3. Locate the last submitted point reported by the database.
4. Submit rows after that point to catch up on data written while the sender was
   offline.
5. Continue watching the file and POST newly appended rows in batches.

Resume matching should prefer a deterministic row identity if available. The
minimum viable identity is:

```text
game_tick + surface + chunk_x + chunk_y + force
```

If that tuple is not unique enough, add a sender-side monotonically increasing
row sequence or byte offset to the server metadata. Byte offsets are fast but
fragile if the TSV file is rotated or rewritten. Row identity is slower to find
at startup but safer across copies and log rotation.

Runtime behavior:

- batch multiple new rows into one `POST /api/ingest/chunk/{savefile_uuid}`;
- retry `503` and transient network failures with backoff;
- treat `400` responses as fatal and print the rejected line number;
- periodically refresh ingest metadata after successful batches;
- handle file truncation or rotation by reopening the file and using metadata
  resume again;
- optionally persist a local checkpoint, but treat the database metadata as the
  source of truth.

The sender should be idempotent enough that resending the final already-accepted
tick is safe. Since the server compares each chunk against live memory and drops
unchanged pixels, duplicate rows should mostly become unchanged-pixel work. If
duplicate same-tick changed rows can occur, add explicit row sequence
deduplication before relying on resend overlap.

## Validation Strategy

Use `chunk-charted.tsv` as the main fixture.

Correctness tests:

1. Import a small TSV sample through the same parser as the HTTP endpoint.
2. Replay the same sample naively into `map[DatastoreKey]map[ChunkCoord][1024]uint16`.
3. Query random chunks at random ticks.
4. Compare database output to naive replay.
5. Include multiple surfaces.
6. Include multiple forces.
7. Include negative chunk coordinates.
8. Include repeated writes to the same chunk at the same tick.
9. Include unchanged chunk snapshots and verify unchanged pixels are discarded.
10. Restart after ingest and verify chunk frame/index recovery.

HTTP tests:

```text
POST one valid row
POST multiple valid rows
POST malformed row returns 400
POST oversized body returns 413
POST under backpressure returns 503
GET queried chunk after POST sees new pixels
GET ingest metadata reports latest accepted rows
```

Tail sender tests:

```text
start from empty database and send full existing file
start with database already partially ingested and resume from metadata
catch up rows appended while sender was offline
watch and send newly appended rows
retry transient server failure without losing rows
handle file truncation or rotation by metadata resume
avoid duplicating data after restart
```

Benchmark metrics:

```text
rows_ingested_per_second
pixels_compared_per_second
changed_pixels_stored_per_second
average_http_ingest_latency_ms
query_p50_ms
query_p95_ms
query_p99_ms
chunk_recovery_time_ms
live_memory_bytes_by_datastore
```

## Initial Implementation Phases

### Phase 1: Format and datastore model

- Add `DatastoreKey`, `ChunkCoord`, and RGB565 chunk types.
- Add datastore registry keyed by `(savefile_uuid, surface, force)`.
- Add dynamic chunk state instead of fixed 2000x2000 tiles.
- Replace palette IDs with RGB565 `uint16` pixels for the Factorio path.
- Add chunk TSV parser and decoder for `chunk-charted.tsv`.
- Add tests for base64 RGB565, negative chunk coordinates, surfaces, and forces.

### Phase 2: HTTP ingest

- Open `serve` databases read-write when ingest is enabled.
- Add `POST /api/ingest/chunk/{savefile_uuid}`.
- Add `GET /api/ingest/chunk/{savefile_uuid}/meta`.
- Stream and parse TSV request bodies.
- Route rows to datastore/chunk workers.
- Compare against live in-memory snapshots.
- Store only changed pixel events.
- Return ingest stats JSON.

### Phase 3: Chunk storage and queries

- Add `.cdat` and `.cidx` chunk file formats.
- Write chunk delta frames and snapshots.
- Implement `ChunkAt`.
- Add latest-state query from live memory.
- Add historical query from snapshot plus delta replay.
- Add map tile rendering over dynamic chunks.

### Phase 4: Durability

- Use `.cdat` as the append-only durability log.
- Add atomic index updates per chunk.
- Ignore unindexed trailing frames after a crash.
- Add crash/restart tests.

### Phase 5: Performance and tooling

- Add chunk worker pool and compression worker pool.
- Add snapshot cache for historical chunk queries.
- Tune delta frame and snapshot thresholds using real `chunk-charted.tsv`.
- Add `import-chunk-tsv`, `tail-chunk-tsv`, `query-chunk`, `stats`, and `inspect-index`.
- Add pprof endpoints for CPU and memory profiling.

## Open Decisions

These should be decided before locking the HTTP contract:

1. Exact `colordata` wire encoding: base64 raw RGB565, hex, or another mod
   output format.
2. RGB565 byte order from the mod. The plan assumes little-endian.
3. Whether invalid rows reject the whole request or return per-line errors.
4. Whether `serve` should always enable ingest or require `--enable-ingest`.
5. Whether historical query APIs should use ticks only, or also accept elapsed
   seconds converted at an assumed tick rate.
6. Whether inactive datastores should evict live snapshots from memory and
   reload from disk on demand.
7. Whether tail resume should be based on row identity, byte offset, or an
   explicit sender-provided row sequence.
